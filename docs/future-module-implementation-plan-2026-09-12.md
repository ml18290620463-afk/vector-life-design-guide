## 1. 核心判断与范围

Vector 的价值不是让用户完成更多事项，而是让真实经历帮助用户选择、行动与调整生活。未来模块应支持长期愿望和每日安排，但不能另建一套与“现在”“过去”竞争的日记或任务系统。

采用两个前台入口：**愿景｜计划**。两个入口是信息组织方式，不代表底层只有两种数据。

- 愿景：我想靠近什么样的生活，可以暂时没有指标、期限和行动。
- 计划：我准备实现什么，以及准备在什么时候做什么。目标与行动在这里相互关联。
- 用户可以直接建立一个目标，也可以只安排一件事；不强迫先写愿景。
- 行动完成、目标进度、愿景实现是三回事，不能相互自动等同。
- 日常安排是必要能力，但看板、工时、复杂优先级、全年任务自动拆解不是本轮范围。

### 1.1 第一版做什么

1. 愿景的创建、修改、暂停及关联目标。
2. 目标的创建、修改、暂停、结束、完成及重新开启。
3. 两类目标：可计量成果、非量化探索。后者用文字进展和用户判断，不展示虚构百分比。
4. 一次性行动：未安排、指定日期、完成、取消、撤销完成；目标关联可选。
5. 手动确认成果计入目标，支持关联既有经历，或一次保存经历与进度。
6. 进度纠正、来源删除、达标归档、备份恢复。

持续实践如“每周运动三次”暂时可记录单次行动，但**第一版不宣称支持周期达成率和自动循环任务**。循环规则、跨周统计、节假日例外在后续独立设计，不能用每日打卡冒充。

### 1.2 明确不做

不改首页观测仪，不重做全站配色，不增加第五个主模块，不复制原则／模式库；不由 AI 决定人生愿景、修改用户原则或自动归档；不以 Mem0、Graphiti 上线为前置条件；不设置生命评分、惩罚式断签或强制复盘。

## 2. 四个模块的边界

| 模块 | 主责与完整内容归属                                 | 可展示的跨模块引用               | 不应承担                           |
| ---- | -------------------------------------------------- | -------------------------------- | ---------------------------------- |
| 过去 | 已发生的经历；已确认模式；用户原则；已结束目标摘要 | 目标名、来源链接、相关行动引用   | 今日待办、进行中目标的第二套编辑器 |
| 现在 | 记录当下事实和结果；承接从行动进入的记录表单       | 正在记录的行动、目标、拟计入成果 | 与未来并列的完整日计划列表         |
| 未来 | 愿景、目标、行动安排、目标进展与生命周期           | 经历标题及日期、原则名称         | 再保存一份经历正文；自动制造模式   |
| 分身 | 调用已有上下文，澄清目标、提出安排和关联建议       | 可跳转到原对象的简短建议         | 第二套目标库；替用户确认愿景或成果 |

同一数据可以被引用，但完整内容只有一个主要归属页。跨页跳转携带对象 ID 和返回位置，不能复制正文或生成第二个可独立编辑的副本。

目标完成摘要放入“过去 → 记录”的时间线，不增加第四个顶层标签。摘要不是 DiaryEntry，不计入普通记录数量，也不进入模式提取材料。用户主动写的完成感受仍是一条正常经历。

## 3. 页面与低负担交互

### 3.1 愿景

列表只呈现愿景文字及关联目标数量。操作：`写愿景`、点击编辑、`关联目标`。不展示“愿景完成度”。

编辑仅要求愿景正文；原因、时间范围可选且收起。不能从高频日记标签自动生成正式愿景。旧 guidingStars 只有经来源核对、确为用户主动写下的内容，才可在迁移时转为愿景。

### 3.2 计划

同一页面纵向两区，不再增加第三组主导航：

1. **目标**：展示名称、当前进度或最近进展、可选期限。点击进入目标详情。目标多时渐进加载，不挤成横向小卡片。
2. **行动**：`今天｜待安排｜以后`筛选；日期选择用于查看任意一天。`已完成`收在次级入口。逾期显示原日期并允许改期，不自动滚到今天制造积压。

目标详情负责完整编辑：成果定义、进度历史、关联愿景、相关行动。页面只保留一个主要新增按钮；点击 `新增` 后选择 `目标` 或 `行动`，不在每个空区域重复引导。

### 3.3 建立目标

默认只填名称，保存为不带数量的目标即可。用户展开 `衡量方式` 时选择：

- `累计数量`：目标量、单位；例如 10 座山。可选 `不重复计数`。
- `文字进展`：例如探索适合自己的职业方向。只记录进展，不显示 0%–100%。

愿景、期限、事件标签均可选。沿用现有事件标签，不引入心情标签或强制分类。给“爬十座不同的山”的建议表单可预填“不重复”，但保存前需用户确认，不把自然语言推断直接作为规则。

### 3.4 行动与结果

安排一件事只需要名称；日期、关联目标可选。一个行动默认最多关联一个目标，先避免多重归属选择。一次真实成果可以由用户明确计入多个目标，各自独立计量，不能自动全部累加。

完成准备行动（如买登山鞋）：直接标记行动完成，不增加目标进度，不弹出日记表单。

完成已声明会产生成果的行动（如登顶黄山）：打开短表单 `完成情况`，预填目标与成果；用户可 `计入进度` 或 `仅完成行动`。`写下经历`、`关联已有记录`均为可选，不能要求每次打勾都写反思。

从“现在”写经历时，提供可选 `关联目标`。已有行动上下文自动带入，不重复询问。没有明确确认计量值，就只保存经历，不更新进度。

### 3.5 达标与过去

达到 10/10 显示 `已达标` 和 `完成目标`，不会自动结束目标或愿景。点击完成后建立一个稳定的完成摘要；不再强制确认一次“确认保存”。

过去时间线显示：目标名称、完成日期、当时 10/10、`查看成果`。现有经历继续在原时间点显示；摘要只引用，不复制。目标完成后仍在未来的已结束筛选中可查，不在两个默认列表同时占位。

## 5. 领域模型规格

以下为类型设计草案，实施时补齐品牌 ID、运行时校验与导出。不要将全部字段直接映射成前台必填表单。

```ts
type DateOnly = string; // 严格校验 YYYY-MM-DD；不是 UTC 午夜时间戳
type GoalStatus = 'active' | 'paused' | 'completed' | 'ended';
type Measurement =
  | { kind: 'quantity'; target: number; unit: string; precision: number; distinctItems: boolean }
  | { kind: 'narrative' };

interface Vision {
  id: string;
  text: string;
  status: 'active' | 'paused' | 'archived';
  createdAt: number;
  updatedAt: number;
  revision: number;
}

interface Goal {
  id: string;
  title: string;
  visionId?: string;
  measurement: Measurement;
  status: GoalStatus;
  startDate?: DateOnly;
  dueDate?: DateOnly;
  tags: string[];
  createdAt: number;
  updatedAt: number;
  revision: number;
}

// 扩展当前 ActionItem，不创建第二套 Action 类型与存储。
interface ActionFutureFields {
  goalId?: string;
  scheduledOn?: DateOnly;
  resultIntent?: 'preparation' | 'outcome';
  revision?: number; // 旧数据迁移初始化
}

type ProgressValue =
  | { kind: 'quantity'; amount: number; itemId?: string }
  | { kind: 'narrative'; note: string };

interface ProgressEvent {
  id: string;
  goalId: string;
  operationId: string;
  semanticKey: string;
  value: ProgressValue;
  occurredOn: DateOnly;
  sourceEntryId?: string;
  sourceActionId?: string;
  sourceState: 'linked' | 'standalone' | 'source-deleted';
  confirmedBy: 'user';
  status: 'valid' | 'revoked';
  replacesEventId?: string;
  goalRevision: number;
  createdAt: number;
  revokedAt?: number;
}
```

补充存储对象：

- `GoalItem`：不重复计数目标中的明确对象，字段 `id/goalId/label`。用户选择或建立“黄山”，持久化 itemId；不同别名可由用户合并。AI 可建议相同对象，但不能擅自合并。
- `GoalRevision`：目标内容、指标、期限修改前后的快照和生效时间。改 10 座为 12 座保留原目标；已有历史摘要不被重写。
- `GoalClosure`：结束时快照、当时有效 progressEventIds、完成/主动结束原因、时间；每个目标一次结束周期只有一个 closure。重新开启保留历史事件，时间线只用一个稳定 goal ID 聚合摘要，详情可查历次结束。
- `OperationReceipt`：operationId、输入摘要、结果对象 ID、提交版本；不包含额外日记正文。用于重试和恢复，不引入通用事件溯源框架。

不存独立可任意更新的 `goal.currentCount`。数量由有效 ProgressEvent 派生，缓存必须可重建；探索型只派生最近文字进展，不返回百分比。愿景不派生完成率。

### 5.1 计数、日期与修改

1. 普通累计：对有效 amount 求和；金额或小数类量按 precision 转换为整数最小单位运算，禁止浮点累计误差。
2. 不重复模式：每个有效 itemId 贡献 1，不通过日记条数、行动完成数计数。不重复模式第一版只支持整数对象计数。
3. amount 必须有限、正值且符合精度；负调整使用撤销／替换旧事件，不给用户一个无法追溯的负数输入框。
4. 每次纠正撤销旧事件并创建替代事件，记录 replacesEventId；不把旧事件仍算在总数里。
5. 日期安排使用当地日期字符串；创建／更新时间使用时间戳；保存成果时明确当地日期。跨时区不把“周六爬山”变成周五。
6. 更换单位或切换 distinctItems 会改变统计意义：有进度后禁止直接改，必须预览重分类结果并确认；复杂换算第一版提供新建目标并保留旧目标，不能默默转换。
7. 超额完成保留真实值如 11/10，视觉进度条可上限 100%，文字不截断事实。

## 6. 命令、存储与一致性

### 6.1 单一写入路径

建议新增领域仓库服务，现有 useDiaryData/useActionItems 改为调用服务并订阅提交结果，不能继续从旧 React 闭包取整份数组覆盖新数据。

```ts
type CommandResult<T> =
  | { ok: true; value: T; revision: number; replayed: boolean }
  | {
      ok: false;
      code: 'validation' | 'conflict' | 'locked' | 'storage-unavailable' | 'storage-full';
      message: string;
    };

// 关键命令名，具体参数实现时从共享领域类型导出：
// createVision / updateVision / createGoal / reviseGoal
// scheduleAction / completeAction / undoActionCompletion
// recordOutcome / correctProgress / revokeProgress
// closeGoal / reopenGoal / deleteEntriesWithImpact
```

`recordOutcome` 接受 operationId、可选经历草稿或既有 entryId、可选 actionId、用户确认的目标成果数组和 expectedRevision。其结果返回 entryId、actionId、progressEventIds。正文只保存于 DiaryEntry；ProgressEvent 只存必要计量信息。

### 6.2 事务方案：同库原子提交，不用 Promise.all 冒充事务

优先复用现有 IndexedDB 数据库／object store。通过现有 idb-keyval 的底层 store 回调或薄原生 IDB 适配器，在**同一个 readwrite transaction** 内读取最新值、校验版本并写入受影响的 entries、actions、futureState、receipt。

实施前确认 idb-keyval 当前 store 定义；若选用 setMany，它只负责多键原子写，不能替代读—校验—写事务和并发版本校验。

1. 表单外完成校验、加密等异步准备，稳定生成 ID；事务期间不 await 网络／AI／加密，避免自动结束。
2. 事务内重新读取相关对象及 revision；冲突返回可恢复错误，不能覆盖另一个标签页的更新。
3. 同事务检查 receipt、semanticKey 和 distinct item 的重复；写入实体与 receipt；等待 transaction complete 后才发布成功。
4. 更新内存状态并通知其他标签页重新读取。BroadcastChannel 是失效通知，不是锁；并发正确性来自数据库事务。
5. hydration 完成前禁用写入。旧标签页通过存储版本握手被要求刷新；仍可使用旧写入协议的页面不能与新版本共同写库。
6. 所有涉及这些 key 的入口（包括导入、删除、批量编辑、旧 addAction）必须接入同一个仓库。不能只改未来页，把旧写入竞争留给现在页。

### 6.3 降级与诚实反馈

跨对象成果保存不降级为分散 localStorage 写入：发生故障保留表单、显示 `未保存 · 重试`，不显示成功。重试复用 operationId。

用户可明确选择 `仅保存记录`：通过独立记录命令保存，成功后显示 `记录已保存，进度未更新`，保留后续关联入口；这不是系统静默丢弃进度。如果底层所有持久化均不可用，保留当前草稿并提供复制内容，不声称草稿已跨刷新保存。

普通日记的现有 localStorage 降级如保留，必须检查返回值、区分存储来源版本，在恢复 IDB 时先做一致性恢复。未经测试的混合存储不能用于关联成果事务。

### 6.4 幂等不仅是按钮禁用

- 同一次操作重复发送：operationId 命中回执直接返回第一次结果；相同 ID 不同输入摘要返回冲突。
- 同一经历同一目标同一成果：稳定 semanticKey，如 `entryId:goalId:outcomeSlotId`；outcomeSlotId 在编辑过程中稳定。
- 没有经历：使用稳定 actionId/resultSlotId 或成果编辑会话 ID。
- 重复爬同一座山：由 goalId + itemId 的有效性约束兜底，与 requestId 无关。
- 编辑记录不能重新添加整套成果；比较稳定成果槽位后纠正原事件。
- 不依赖文本相似度去判断金融式精度的计数；模型输出只是待确认候选。

## 7. 生命周期、删除与隐私

### 7.1 状态规则

- 暂停目标不删除进度；未来日期的关联行动列出影响，用户选择保留或取消，不能一并消失。
- 完成目标与主动结束分开；结束原因可选，不要求解释“为什么失败”。
- 达标不自动完成；重新开启不清零。可以独立调整新期限与目标量。
- 撤销行动完成默认只恢复行动状态；若它附有成果，显示 `同时撤回进度` 选择。不能撤销一张任务卡就悄悄抹掉真实经历。
- 已完成目标的成果被撤回后，当前统计据实变化；历史摘要保留“完成时 10/10”，详情显示当前校正值及 `重新开启`。不得继续把当前 9/10 伪装成已达标。

### 7.2 删除影响规格

| 删除对象       | 默认影响预览                                     | 用户可选项／边界                                                                                            |
| -------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| 经历           | 列出相关模式、原则及目标进度数量                 | `模式与原则：保留／一并删除`沿用现有规则；有进度才增加独立项 `目标进度：保留／撤回`，不得隐式共用一个布尔值 |
| 经历，保留进度 | 删除正文、来源链接，保留经用户确认的最小成果事实 | sourceState 标为 source-deleted；不保留正文摘要；目标对象名仍可能敏感，确认中说明仍会保留成果名称           |
| 经历，撤回进度 | 相关有效事件撤销，统计重算                       | 删除来源引用；检查已完成目标当前是否不再达标                                                                |
| 行动           | 删除安排和行动来源引用                           | 已有真实经历、已确认成果默认保留，影响面板允许另行撤回                                                      |
| 目标           | 展示关联行动及成果影响                           | 优先用 `结束`；彻底删除移除目标专属进度／历史／去重对象，保留独立经历；关联行动选择独立保留或删除           |
| 愿景           | 展示关联目标                                     | 默认保留目标并解除关联，不级联删除人生经历                                                                  |

只有存在关联时才显示对应选择；破坏性批量删除需明确选择后提交，不默认勾选“一并删除”。知识保留与删除细节继续遵循过去模块已有来源规则，不在本次重定义多来源原则的判定。

删除不等于业务撤销：普通撤销保留必要历史；用户明确删除敏感内容时清理其正文、缓存、内部恢复副本和相关来源信息，不能以“账本不可变”为由永久保留文本。外部模型／记忆服务只有确已启用时才纳入实际删除队列，并真实报告远端状态。已下载到用户设备之外的备份无法远程抹除，需说明恢复旧备份可能重新带回内容。

### 7.3 安全边界

现有 vault key 多为全局，此计划按单本地 vault 实施，不宣传多用户隔离。未来对象的标题、文字进展和目标名称同样属于个人数据；实施前核对现有加密与锁定链路，并纳入相同保护边界，不能仅锁住 UI 却声称全部已加密。

锁定时不展示相关愿景、目标或来源，也不发起 AI 提取。不把正文写入 debug 日志、操作回执、遥测和 localStorage 草稿。第一版若不能实现一致的保护策略，相关写入功能不能发布给受保护 vault。

## 8. 迁移、备份与恢复

1. 新增 schemaVersion 和单一 futureState 存储键，涵盖 visions/goals/items/progress/revisions/closures；actions 继续使用原集合。所有 key 加入同一存储清单及 wipeData。
2. 迁移事务幂等；先验证原数据可读并保留受保护恢复点，成功后写完成标记。失败保留原数据，不能回退成示例数据冒充恢复成功。
3. 旧 ActionItem 保留原 ID、状态、时间及原则／经历链接；没有 goalId 的行动作为独立行动。旧 completed 不能推算成任何目标进度。
4. guidingStars 只迁移来源确定的用户文本；不确定内容留待用户主动采用。旧 direction/path 决策文案不自动转目标。
5. 普通完整备份升级为 v2：entries、principles、patternPrincipleLinks、actions、futureState，以及需要保留的用户确认模式数据；实施时枚举真实持久化集合，派生向量可重建、不强行导出。若沿用备份签名，同步升级校验覆盖的载荷。
6. v1 导入只操作旧版包含的数据，不能把缺席的 futureState 解读成“清空未来”；替换日记前检查现有目标来源影响并要求确认。
7. v2 导入先校验字段、引用、operationId、schema 和语义去重，再预览合并／替换影响；按 vault 级事务提交。跨备份 ID 碰撞统一重映射所有引用或报冲突，不逐数组盲目拼接。
8. 完成摘要、历史目标量、撤销事件、保留进度但删除来源的状态必须能 round-trip。未来更新版本的备份明确拒绝，禁止静默丢字段。
9. 导出普通文本记录保持原能力；与“完整备份”明确命名区分。数据库恢复副本不是用户可迁移的完整备份。
10. 清空数据同步清除新增键、镜像、内部恢复副本、操作回执与内存状态。迁移回滚只在尚未产生新版本写入时可直接恢复旧版本；产生新数据后必须先导出或前向修复，禁止用旧程序覆盖新数据。

## 13. 最终实施原则

界面可以简单，数据关系不能含糊。首要交付不是两张漂亮页面，而是：**用户只记录一次，系统准确计入一次；允许改变主意，允许纠正，能够恢复；过去保留事实，未来保留选择。**
