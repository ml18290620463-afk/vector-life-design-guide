# Journey / Odyssey AI 深度研究与 VECTOR 优化建议

研究日期：2026-10-09。基于官方文章、现行网站、官方 GitHub 与 VECTOR 当前工作区源码。本文是产品与工程研究，不代表实际安装体验、生产安全审计或模型效果测评。仓库已有大量未提交修改，分析包含当前工作区内容；本次仅新增本文。

## 1. 结论

Journey 最值得借鉴的是让积累的日记变得可问、可找、可回看：用户用时间、人物、情绪和地点等生活语言，直接访问过去。VECTOR 可以在此之上建立更完整的路径：经历 → 识别模式 → 确认原则 → 选择行动 → 回收结果 → 修正理解。

VECTOR 已有这条闭环的数据与上下文基础，但“已有数据进入模型”尚不等于“模型能可靠理解人生”。下一阶段优先补齐时间查询、确定性统计、多线索检索、用户可纠正的证据和真实效果验证。多媒体、地图、社交渠道与庞大知识图谱可以后置。

没有在本次核实的官方仓库中发现 Odyssey AI 的公开实现。Journey 的公开 GitHub 主要提供自托管同步说明与部署模板；不能据此复刻其 AI，也不能把同步服务器的技术栈当作 Odyssey 检索架构。

## 2. Journey 的产品机制

### 2.1 2023 年的 Odyssey 文章实际承诺什么

[发布文章](https://blog.journey.cloud/introducing-journey-odyssey-ai-deepening-your-self-understanding-through-ai-journal-based-responses/)发表于 2023-12-26，宣布 2024-01-01 Web 上线，后续文章更新记录移动与桌面端扩展。

核心能力是基于日记历史的自然语言问答。官方例子包括：上周的心情、某几个月的健身目标、今年写了多少篇日记、什么使自己开心、感恩、旅行、与母亲有关的记录。这些例子实际覆盖五类任务：

| 用户任务     | 系统应解决的问题           | VECTOR 可借鉴之处            |
| ------------ | -------------------------- | ---------------------------- |
| 找一段经历   | 时间、主题、人物的组合检索 | 用生活语言查原始记录         |
| 算一个事实   | 年度篇数等确定性聚合       | 在本地算出答案后交给模型表述 |
| 总结一个时期 | 在完整时间范围内汇总       | 区分记录覆盖与真实生活全貌   |
| 看一个变化   | 比较不同阶段               | 连接模式、原则、行动结果     |
| 理解自己     | 从记录提出有根据的解释     | 提出可纠正假设，避免人格裁决 |

早期入口为登录 Web → 选择 Journey Cloud Sync → 至少 10 条日记 → 打开 Odyssey → 同意条款 → 提问。10 条门槛是该文章描述的启动规则，不应直接当作 VECTOR 的合理门槛，也未核实它是否仍是全部平台当前规则。

其产品优势在于用户不用记住分类、搜索词和记录日期。过去的内容从“仓库”变成了可交流的个人资料。模板、提醒与回顾则帮助持续积累，积累又提高检索价值。

### 2.2 2026 年的 Journey 已超出一个 AI 日记聊天窗口

[官网](https://journey.cloud)当前展示多平台客户端、图文视频音频记录、日历、媒体浏览、Atlas 地点、心情追踪、往日回顾、共享日记、邮件记录、教练模板、导出与健康相关插件。

[2026-07-08 WhatsApp 文章](https://blog.journey.cloud/chat-with-your-journey-journal-on-whatsapp/)进一步把记录和历史问答放进既有聊天渠道，支持文字、图片、媒体和语音等输入。可借鉴的本质是降低记录成本与让回忆发生在日常场景中。VECTOR 可以先优化自己的短句捕获与自然追问，再判断是否值得承担外部消息渠道的账号、隐私、媒体存储和同步复杂度。

这些功能表明 Journey 是成熟的日记平台，Odyssey 是利用历史资料的服务层。不能以一篇 AI 发布文章概括整个应用，也不能把官网功能列表视为每个平台每个套餐都具备的已验证体验。

### 2.3 需要谨慎对待的产品表达

文章的“谁是我最好的朋友”等问题容易诱导系统把提及次数和文字情绪等同于关系质量。VECTOR 应答复“你记录中经常出现谁、出现在哪些场景”，将解释交给用户确认。类似地，少写负面经历不等于心情改善；运动后心情较好不证明运动是唯一原因；未记录结果不等于行动失败。

Mem0 当前 README 描述 2026 新算法为 ADD-only、实体关联、多信号检索与时间推理；同时明确其公开的高分来自含专有优化的托管平台。不能将这些分数直接当成开源 SDK 或 VECTOR 的效果，也不应照搬“代理产生的事实与用户事实同等权重”：VECTOR 的自我理解应继续区分用户确认与 AI 假设。

Graphiti 描述双时间与事实失效管理，默认涉及模型服务与图数据库，也支持其他/本地模型配置。它适合关系与时间复杂度已经超过本地结构能力的情况。VECTOR 当前 provider 接口中 mem0、graphiti 的 pending 标记并不是已完成集成。

复用优先级：产品任务与数据语义 > 检索与评估方法 > 合适的部署模板 > 新增平台依赖。暂时没有证据表明引入 Journey 的服务器组件会解决 VECTOR 当前最关键的问答问题。

## 4. 技术公开范围与隐私边界

发布文章称使用 GPT、上下文与情绪分析，并宣称查询处理后丢弃、敏感信息遮蔽。它没有披露可核实的模型版本、提示词、切片策略、向量数据库、检索召回率或效果实验。这些隐私描述属于厂商声明，本次没有独立审计。

一个合理的实现方案是“问题解析 → 权限与时间过滤 → 检索/聚合 → 证据组织 → 模型回答”。这是本文对 VECTOR 的设计建议，不能标注为 Journey 已公开架构。

[官方加密说明](https://support.journey.cloud/categories/synchronization-cloud/articles/how-does-encryption-work-in-journey)，更新于 2025-08-18，描述可选 Journey Cloud Sync 端到端加密、用户口令、设备端加密与不保存口令；同时说明原始媒体会先上传处理再加密，部分日期等元数据不加密，开启加密后服务器搜索不可用，且开启不能撤销。缓存原始媒体销毁亦为厂商声明。

因此“支持 E2EE”需要逐项分析文字、媒体、元数据、索引与 AI 请求。该说明不能单独证明 Odyssey 与加密日记能否协同工作，本次未得到明确兼容性材料。Odyssey 专门隐私政策全文亦未成功核实，不扩大推断。

VECTOR 本地优先也不等于所有 AI 都在本地：外部模型收到的选中上下文构成另一条信任边界。备份加密则只覆盖导出的文件，不自动覆盖浏览器本地存储。

以 PROJECT_OVERVIEW.md（2026-10-08）、五批次交付记录和当前源码为依据。旧 Memoir、Morning Star、角色等退役模块不作为现行能力。

### 关键代码定位

- `services/avatarGuidance.ts`：普通问题先通过字符 bigram 排序挑选一条种子，再扩展关联，最多约四个来源；固定引导有不同类型选择。不是对全部记录的时间汇总，也不是简单的“最高分前四条”。
- `features/now/state/avatarGuidanceContext.ts`：续问利用之前的实质性问题；首次入口可锚定记录/行动，换话题后解除；身份类记忆另有限额。
- `services/avatarGuidanceSources.ts`：组织原始经历、原则、模式、行动、目标和结果等来源。
- `services/neuralSemanticRecall.ts`：现有本地神经检索、内容指纹、分批更新与余弦排名。
- `services/semanticEmbedding.worker.ts`：中文 bge-small 模型、q8、WASM、Worker，配置只使用本地模型路径。代码存在不等于每台设备都有模型资源并能流畅运行。
- `features/now/NowFlow.tsx`：已调用神经关联记录检索；当前 Avatar 上下文路径未发现该接入。
- `services/avatarIntelligence.ts`：结构提取等 provider 抽象与本地启发式实现；不能表述为完整语义知识图谱上线。
- `features/now/api/avatarModel.ts`：“记住配置”会把含 API key 的配置写入 localStorage。
- `services/semanticEmbeddingStore.ts`：向量记录直接写 IndexedDB，未见该层加密；向量也是敏感派生资料。
- `docs/testing/vector-five-batch-delivery-2026-10-07.md`：交付与测试记录，同时指出真实模型评估待做、Avatar 旧 localStorage 缓存仍明文。历史测试数量未在本次重跑。

## 6. 六项高价值优化

### P0-A：先确定问题类型，再选择计算或检索

引入统一查询计划，可表达 intent、时间范围、实体、来源范围、权限和历史/当前视角。区分事实寻找、精确统计、时期总结、变化比较、当前选择，不让所有问题都走一条种子检索。

“今年写了多少条？”先在本地按定义过滤与计数，模型只解释确定结果。需约定样例、删除记录、解锁记录、补记、去重与时区口径。“上周我为什么总是累？”先确定上周的日历边界，再找完整范围中的相关经历，不能只拿几条命中结果代表全周。

建议默认使用用户当前时区；将用户可见的“上周”解析为明确起止日期。分别记录事件时间、记录创建时间与记忆有效期。历史问题可访问当时有效的旧理解，但必须标为历史；已撤回或禁止访问的来源不能借历史查询恢复。

验收：跨年、月底、周一、补记和不同时间区测试；精确统计与本地可信集合完全一致；没有记录时不生成内容。时间解析不明确时允许一句必要澄清。

### P0-B：把已有语义检索接入 Avatar，并保留精确词检索

重用现有 Worker 与向量缓存，先做多条独立种子，再做受预算约束的关联扩展。关键词负责人名、金额、专有名词；语义负责“被否定”和“努力没有被看见”等不同说法；时间与权限在检索前执行；结果与反例避免仅召回支持既有判断的资料。

可尝试融合 bigram/BM25、向量与已有关系，比较混合检索对基线的收益。不要在未验证之前规定更大的固定 top-k，也不要直接将完整日记库发送模型。对多时期汇总应分批覆盖后汇总，而非沿用四来源上限。

现有神经检索只索引记录标题/正文/标签；原则、目标等其他类型需要各自的文本投影和版本，不能假定记录向量覆盖全部资料。现有候选过滤还需统一接入 Avatar 的来源限制。

验收：建立含同义表达、人名、多次独立事件、相反结果和受限来源的数据集；测 Recall@k、证据精度、禁用资料泄漏、冷/热启动耗时与内存。模型不可用时明确回退关键词检索，中文模型跨语种效果需另测。

### P0-C：验证 AI 是否因历史而更有用

利用已有 80 行为场景继续做真实模型评估。比较当前对话、当前 lexical 记忆、混合记忆三种条件，使用同一模型配置与盲评。开发集调参，独立保留集验证，避免把场景期待语句机械写进提示词后宣称泛化。

覆盖多轮换话题、旧目标结束、结果撤回、记忆被纠正、时期比较、无记录、关系推断与日记内恶意指令。历史记录只能是证据数据，不能覆盖系统规则或触发执行行为。

分别测检索正确、时间正确、统计正确、续问连贯、解释可纠正和帮助选择。禁止访问/撤回内容泄漏与严重边界错误必须为零；85% 相关性、90% 连贯性属于现有规划目标，尚不是测得成绩。失败就定位为检索问题、数据语义问题或生成问题。

然后做 6–8 人任务研究与 2–4 周试用。长期成功指标应包括用户确认的有效行动、修正成本与持续回顾，而不只有对话次数；短期试验不能证明长期成长因果。

### P0-D：补齐本地数据与模型请求的隐私边界

优先盘点原文、对话、记忆、向量、API 配置、备份和请求日志。现有加密备份保留；本地明文缓存与记住的密钥需要独立处理。

本地加密方案要涵盖解锁后生命周期、锁定时清理内存与 Worker、取消待发请求、索引删除与恢复、旧数据迁移与失败恢复。口令加密无法自动防御解锁后的同源脚本攻击，需配合内容安全与依赖管理。若 API key 只是与本地可读的加密密钥一起存放，收益很有限。

界面应说清“记录在本地；本次选中的资料将发给所选模型服务”。可按需展开来源与模型配置，无需每次回答展示大块证据面板。统计问题能本地回答时无需外发。

### P1-A：将抽象入口变成个人当下可回答的问题

保留原有三条方向，并依据真实资料提供具体问题，例如“本周哪些情境让我耗竭？”“上次类似的选择，我做了什么？”“这项原则在哪些行动里有效？”“我对这个目标的想法有什么变化？”

候选问题必须有可访问资料支持；零记录时引导记录一个片段，少量记录时只回看现有经历，不复制 10 条锁定门槛。涉及重复模式时说明“目前只有两次记录，可能只是线索”。

推荐流程：用户选择/输入问题 → 解析时间与范围 → 必要时澄清 → 简洁回答 → 按需看原文 → 用户纠正 → 如需持久记忆则确认 → 用户愿意时形成一个行动 → 之后回收结果。加载、取消、模型失败时保留问题和资料入口；无证据与服务失败分别处理。

### P1-B：以用户主动回顾连接过去与未来

先实现可主动打开的周/月回顾，表达记录覆盖、重复情境、采取过的行动、结果与例外。没有记录的日期不能填为情绪平稳；没有结果的行动显示尚未知；不同阶段比较必须说明样本数量。

输出最多突出几个有证据的变化和一个可选下一步，允许用户拒绝解释或纠正事实。回顾结论保持为临时总结；只有确认后才进入长期记忆。这样可以复用 Journey 的“历史值得重访”，又保留 VECTOR 的原则修正与行动闭环。

## 7. 暂缓事项及取舍

- 不因 Journey 成熟就扩张到地图、共享、打印、健康、邮件和 WhatsApp 全家桶。它们分别需要真实需求与新的数据边界。
- 不恢复已退役的角色或独立回忆录来装载上述能力。优先沿现有 Now/Past/Future/Avatar 结构完善。
- 不直接移植 Journey 镜像到商业化项目；模板与镜像许可不同。
- 不把 Mem0 或 Graphiti 接入当作“记忆问题已解决”。先利用现有 provider 做本地可比较原型，需求和实测收益超过运维成本后再接入。
- 不把聊天里的长期推断自动写成用户事实，不以关系排名、人格标签和诊断作为卖点。

## 8. 执行顺序与完成定义

| 批次     | 交付物                                  | 完成定义                                     |
| -------- | --------------------------------------- | -------------------------------------------- |
| 1        | 查询计划、时间语义、确定性统计          | 边界日期与计数可信，无数据可正确拒答         |
| 2        | Avatar 混合检索复用、统一权限、来源覆盖 | 在保留集提升召回且无权限泄漏，设备成本可接受 |
| 3        | 本地敏感存储盘点与保护、请求说明        | 迁移可恢复，锁定/删除/还原行为一致           |
| 4        | 具体提问入口、按需原文、主动时期回顾    | 用户能找到资料、纠正解释并理解样本局限       |
| 贯穿各批 | 真实模型盲评与用户任务验证              | 改进有证据；失败类型与退化策略可追踪         |

这些批次是建议，不是已经实施的功能。先建立最小评估基线，再逐批修改；否则无法判断新增检索与 UI 是否提高质量。
