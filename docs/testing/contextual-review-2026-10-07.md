# VECTOR：五批次完善与验证记录

日期：2026-10-07。版本标识：`contextual-review-2026-10`。

## 产品要求与取舍

本轮采用“现在记录、过去回看与提炼、分身解释与纠正”的功能分工。认可、不认可、修正通过记录完成或主动提炼后的情境弹窗处理；常态页面不展示依据列表、依据数量或把 confidence 当成正确概率。关闭与 Escape 都只表示暂缓。

这个方向能减少信息负担，但不能让纠正入口随弹窗消失。因此保留“过去 → 沉淀 → 提炼模式”用于重新处理暂缓候选；分身可回答“我的模式有哪些关联经历？”和“原则适用于什么情况？”，也可通过“修正我的模式”选择并纠正已有模式。这是设计判断，尚未通过真实用户研究证实。

## 批次 1：版本与预览来源

- 在最新首页所在的 `codex/home-ui-refinement` 工作树继续修改，保留已有首页、绿色视觉与解锁卡片布局。
- 设置内提供折叠的版本信息，记录构建时间、分支、提交及是否包含本地修改。
- 修复构建版首页在 `.codex` 隐藏父目录下被静态文件规则拦截的问题：从构建根目录内解析首页文件。
- 用户预览地址固定为 `http://127.0.0.1:3010/`；自动化测试使用独立的 3710 端口和独立浏览器数据。

## 批次 2：草稿、隐私、恢复

- 草稿纳入保险库事务及加密、改密、清空路径；旧草稿只有在迁移提交成功后才移除。
- 加载失败时阻止新草稿覆盖旧内容；支持重新读取。自动保存失败保留输入并明确提示。
- 串行保存、版本冲突检测、丢弃标记，防止旧写入覆盖新稿或让已丢弃草稿复活。
- 记录提交前先保存草稿，提交使用稳定编号；退出时等待保存或明确丢弃。
- 支持的完整备份格式升级为 v3，包含草稿；导入不同草稿时报告冲突。
- 恢复文案与行为一致：现有离线凭证是校验凭证，不能解密已经忘记密码的加密数据。

边界：加密保险库的完整备份导入导出仍不支持，不能把本轮描述成所有备份能力都已完成。浏览器在最后一次保存提交前被强制终止，仍可能损失尚未提交的输入；保存状态以实际提交为准。

## 批次 3：情境确认与可纠正理解

- 两条不同且可访问的真实记录才构成规则提炼候选；排除示例、重复编号与不可读取记录。
- 补充他人经历、过去状态、否定、引用、明确反讽、一次例外和计划语境的回归用例。
- 弹窗支持认可、不认可、用户改写、稍后再说；失败不关闭，已有决定被其他页面更新时不静默覆盖。
- 确认使用独立的居中小弹窗，不继承全屏编辑器布局；桌面与手机沿用各自主题色，背景页面仍可感知。
- 保留拒绝、替代状态以抑制同类结论重现；用户改写优先于规则生成措辞。
- 分身查询只将已认可模式作为已有理解，展示真实可读取记录及实际应用反馈；缺少记录、适用情境或例外时明确未知。
- confidence 仅作内部排序，不显示为“正确概率”。
- 移除对话中常驻理解/来源面板和记忆列表中的依据数量；对话提炼由明确操作触发。

边界：提炼仍包含关键词与语境规则，不能宣称已经理解任意反讽或复杂跨句语境。分身的此类证据回答为确定性检索与组织，不是自由语义检索；默认最多列出八项理解及每项五段经历。纠正的序号绑定当时提供的对象编号，避免列表重排导致改错对象。

## 批次 4：流程闭环

- 记录完成步骤依次执行：记忆、原则反馈、行动、模式提炼；失败后保留草稿，重试复用记录编号。
- 原则反馈按记录编号防重；原则与关联状态在同一个事务更新，拒绝失效引用及冲突编辑。
- 行动关联不存在时提示失败，不把未完成步骤当作成功。
- 回到过去时保留当前分区和搜索词；没有承诺恢复滚动位置。
- 正常“沉淀”页可主动提炼和进入分身；写原则的更多设置允许关联已认可模式，不纳入拒绝、待确认或已替代结论。该选择只在主动创建时出现。

### 现在就应满足的质量标准

| 项目                 | 验证方法                                       | 通过标准                                                         |
| -------------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| 草稿不会被旧请求覆盖 | 加载失败、保存失败、异步丢弃与多页面冲突测试   | 旧内容不被静默清空，失败可见，重试可完成                         |
| 决定具有实际含义     | 弹窗与完整交互测试                             | 关闭不等于接受，拒绝不立即重推，修正不被旧文字覆盖               |
| 反馈不重复入账       | 对同一提交重复执行完成步骤                     | 不重复创建记录、不重复增加原则反馈                               |
| 证据可追溯           | 原则经模式关联记录，以及来源删除/锁定/示例测试 | 只解释实际存在且可访问的依据，缺失时明确未知                     |
| 功能分工清晰         | 常态页与主动编辑状态检查                       | 常态页没有认可按钮和证据清单；主动操作能找到确认、纠正与关联入口 |

这些是正确性与可用性底线，不需要等待使用量或留存数据才能修复。

### 必须使用真实体验数据才能判断的事项

以下全部是建议实验与判定规则，不是已经观测到的数据，也不是市场结论。

1. **弹窗是否打断记录。** 第一轮邀请 6–8 名目标用户完成：记录两段相关经历、暂缓候选、重新找到候选、修正措辞。记录完成情况、被打断感受和需要解释的位置。任何把关闭理解为认可的情况都应优先改文案；若 2 人以上找不到暂缓入口，优先改善入口提示，而非增加常驻面板。
2. **分身是否让证据更容易理解。** 请用户不看操作说明，查询某条模式为什么出现、原则何时不适用，并纠正一条错误理解。分别记录能否找到、能否理解、能否完成；如果查不到而非看不懂，先完善提问识别与对话入口。小样本结果报告人数与过程，不包装成准确率。
3. **模式本身是否贴切。** 在明确同意下收集脱敏表达，按他人/过去/否定/引用/反讽/例外/混合语境分层；开发样例与保留评测样例分开。报告各类误报、漏报及无法判断样例，优先压低把别人或过去状态认定为用户当前模式的误报。认可率不能单独代表理解准确率。
4. **原则是否真的有用。** 做 2–4 周小规模自愿试用，追踪“有适用机会 → 选择原则 → 采取行动 → 记录结果”。分别查看有帮助、部分有帮助、无帮助与未应用的原因；不把未点击当作无效，不把反馈分数当作因果证明。
5. **是否值得精简某个功能。** 先确认用户已经看到并理解该功能，再结合任务成功、访谈与持续使用决定合并或移除。不能仅凭低访问量删除恢复、纠正和备份入口。
